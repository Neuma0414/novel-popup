# GitHub ⇄ Gitee 双向同步机制

本仓库同时托管在 GitHub 与 Gitee，两端内容始终保持一致。任一端有新提交，都会在无需人工干预的情况下同步到另一端。

## 一、整体机制

同步完全由仓库内置的 GitHub Actions workflow 驱动，**不需要自建服务器、不需要 Gitee 付费镜像功能**。

```mermaid
flowchart TD
    A["开发者在 GitHub 提交 main"] --> B["push 事件触发 workflow"]
    C["开发者在 Gitee 提交 main"] --> D["定时任务（每 10 分钟）触发 workflow"]

    B --> E["检出完整历史<br/>fetch origin/main 与 gitee/main"]
    D --> E

    E --> F{"比较两端的<br/>main 提交"}
    F -->|两端一致| G["直接结束 ✅"]
    F -->|GitHub 领先| H["force push → Gitee"]
    F -->|Gitee 领先| I["快进 → GitHub"]
    F -->|两端分叉| J{"尝试三方合并"}

    J -->|合并成功| K["保留双方提交<br/>同时推送两端"]
    J -->|合并冲突| L["以提交较新的一端为准<br/>覆盖另一端"]
```

两条触发路径对应两种延迟：

| 触发路径 | 触发方式 | 生效延迟 |
| --- | --- | --- |
| GitHub → Gitee | `push` 事件 | 秒级（Actions 排队时间，通常 10–60 秒） |
| Gitee → GitHub | `schedule` 定时（名义每 10 分钟） | 实测约 17 分钟，高峰期可能更长 |

> 之所以 Gitee 侧要靠定时任务：Gitee 的 WebHook 无法携带 GitHub API 所需的认证请求头，因此不能直接唤起 GitHub Actions。定时拉取是**不依赖第三方中转服务**的前提下最稳妥的做法。

除上述同步逻辑外，workflow 末尾还有一个 **保活心跳**步骤，用于防止定时任务被 GitHub 静默禁用，详见第四节。

## 二、同步行为矩阵

workflow 每次都先比对两端，再决定动作。**GitHub 侧永远先检查 Gitee 是否有新提交，绝不会盲目覆盖**。

| 两端状态 | 执行的同步动作 | 结果 |
| --- | --- | --- |
| 提交一致 | 不操作 | 两端保持原样 |
| GitHub 领先，Gitee 是其祖先 | `force push` 到 Gitee | 两端对齐到 GitHub |
| Gitee 领先，GitHub 是其祖先 | 快进推送到 GitHub | 两端对齐到 Gitee |
| Gitee 仓库为空（首次） | 初始化推送 | 建立 Gitee 的 main |
| 两端分叉，且自动合并无冲突 | 合并双方提交后推送两端 | 双方提交都不丢失 |
| 两端分叉，且合并有冲突 | 以提交时间较新的一端为准覆盖另一端 | 两端对齐，较早一侧的改动被覆盖（见「已知风险」） |

标签（tags）会随分支一起同步，便于两端的 Release 保持一致。

## 三、一次性配置

### 1. 创建 Gitee 仓库

登录 Gitee → 新建仓库：

| 字段 | 填写值 |
| --- | --- |
| 仓库名称 | `novel-popup`（与 GitHub 保持一致） |
| 归属 | 你的个人账号 |
| 是否开源 | 开源（与 GitHub 的公开仓库对应） |
| 初始化仓库 | **不要勾选**，保持空仓库 |

> ⚠️ 保持空仓库很重要：Gitee 若自动创建了 README，首次同步时会产生一个分叉提交，需要多跑一次同步才能对齐。

### 2. 生成 Gitee 私人令牌（PAT）

Gitee 头像 → 设置 → 安全设置 → **私人令牌** → 生成新令牌：

- 权限勾选：`projects`（仓库读写）
- 生成后**立即复制**，页面关闭后无法再次查看

### 3. 在 GitHub 配置 Secrets

进入 GitHub 仓库 → `Settings` → `Secrets and variables` → `Actions` → `New repository secret`，添加两条：

| Secret 名称 | 值 |
| --- | --- |
| `GITEE_USER` | 你的 Gitee 用户名（仓库地址 `gitee.com/<这里>/novel-popup` 中的一段） |
| `GITEE_TOKEN` | 上一步生成的 Gitee 私人令牌 |

> 不要用 Gitee 的登录密码，必须是私人令牌。
> GitHub 侧的推送使用 Actions 内置的 `GITHUB_TOKEN`，无需额外配置。

### 4. 首次对齐

Secrets 配置完成后，进入 GitHub 仓库 → `Actions` → 左侧选择 **🔁 GitHub ⇄ Gitee 双向同步** → 右侧 `Run workflow` → 选择 `main` 分支 → 点击运行。

首次运行会把 GitHub 侧的完整代码推送到空的 Gitee 仓库，之后即进入自动同步状态。

> `Run workflow` 界面上有一个 `force_heartbeat` 复选框，**正常情况下不要勾选**，它只用于验证保活机制（见第四节）。

## 四、日常使用

配置完成后**不需要任何定期人工维护**：

- 在 GitHub 提交 / 合并 PR → 秒级同步到 Gitee
- 在 Gitee 网页或本地提交 → 约 17 分钟（实测）内同步回 GitHub
- 想立即对齐 → Actions 页面手动 `Run workflow`

每次运行的结论会写进 Actions 的 **Summary**，包含触发方式、执行的动作、保活心跳状态、同步后的提交号，便于事后审计。

### 为什么不需要定期打理：关于保活心跳

GitHub 有一条规定：**公开仓库在 60 天内没有任何仓库活动时，`schedule` 类型的 workflow 会被自动禁用**，而且**不发任何通知**。一旦被禁用，Gitee → GitHub 方向的定时同步就会静默停摆，只能人工去 Actions 页面重新启用。

workflow 末尾的「条件心跳」步骤解决了这个问题：

| 项目 | 说明 |
| --- | --- |
| 触发条件 | `main` 上最后一次提交距今超过 **45 天** |
| 动作 | 更新 `.github/keepalive.txt` 并提交，同时推送到两端 |
| 效果 | 60 天计时归零，再过 45 天又会心跳一次，形成自维持循环 |
| 为什么取 45 天 | 早于 GitHub 的 60 天阈值，定时任务还来不及被禁用就已经被续期 |
| 代价 | Gitee 镜像历史里大约每 45 天多一条心跳提交 |

心跳提交使用 Actions 内置的 `GITHUB_TOKEN` 推送。GitHub 规定内置令牌触发的 push **不会再唤起新的 workflow 运行**，因此不会形成循环触发，也**不需要额外配置任何长期凭据**。

> **想立刻验证保活是否生效**：Actions → `Run workflow` → 勾选 `force_heartbeat` → 运行。结束后两端会各多一条心跳提交，Summary 的「保活心跳」一行会显示结果。
>
> **想停用保活**：删除 workflow 中的「条件心跳」步骤即可；此后若仓库连续 60 天无提交，需要自行到 Actions 页面点 `Enable workflow` 恢复。

### 关于令牌有效期

| 令牌 | 建议有效期 | 原因 |
| --- | --- | --- |
| GitHub 私人令牌 | 7 天或更短 | 仅在本地建仓、首次推送时使用一次，不进入 workflow、不写入任何文件，用完即可吊销 |
| Gitee 私人令牌 | **永不过期** | 用于持续同步，设短期会在到期后静默停摆 |

> Gitee 令牌生成后**不能修改有效期，只能删除重建**，因此必须一开始就定对。如果确实不想用永不过期，请自行安排续期提醒。

## 五、查看同步状态

| 想看什么 | 去哪里 |
| --- | --- |
| 最近一次同步结果 | GitHub 仓库 → Actions → 🔁 GitHub ⇄ Gitee 双向同步 |
| 同步动作明细 | 点开某次运行 → 展开「比对两端并单向收敛」步骤 |
| 两端是否一致 | 对比两端仓库首页显示的 main 最新提交短哈希 |

## 六、延迟与限制

| 项目 | 说明 |
| --- | --- |
| Gitee → GitHub 延迟 | 名义每 10 分钟，**实测约 17 分钟**。GitHub 的 `schedule` 不保证准点，会按平台负载排队延后，高峰期更长 |
| 定时最短间隔 | GitHub 的 cron 最短为每 5 分钟一次，本仓库使用 10 分钟 |
| Actions 配额 | 公开仓库的 Actions 完全免费、不限分钟数。若改为私有仓库，每月的 2000 分钟免费额度会被这种高频定时大量消耗，可能超出 |
| 定时任务保活 | 已内置条件心跳，无需人工介入（见第四节） |
| 同步内容 | **仅 `main` 分支**的提交与标签。在任一端新建的其他分支、以及 Issues / PR / Wiki / Releases / 仓库设置等平台侧数据都不在同步范围内 |
| Git LFS | 未启用，本仓库不使用大文件 |
| 强制推送 | 同步是镜像语义，会对目标端执行 force push |

## 七、已知风险

1. **两端在短时间内同时提交**：如果在一个定时周期内（实测约 17 分钟）两端各有新提交，会走「分叉」分支。无冲突时自动合并、双方提交都保留；有冲突时以较新的一端覆盖另一端，**较早一侧的改动会丢失**。
   → 建议：尽量只在一端提交。若确实需要两端同时开发，先在其中一端 `git pull` 对齐，再提交。

2. **GitHub Actions 不可用时**：GitHub 侧提交仍会推进 GitHub，但不会外发；Gitee 侧提交也无法回传。恢复后下一次定时任务会自动补齐。

3. **令牌失效**：Gitee 私人令牌过期或被吊销后，workflow 会在「配置远端与提交身份」步骤直接失败并给出明确报错，不会静默跳过。

4. **定时任务被 GitHub 自动禁用**：公开仓库连续 60 天无仓库活动时会发生。本仓库已用「条件心跳」在 45 天处自动续期，正常情况下不会触发。若因异常（例如 workflow 自身长期失败，导致心跳也没跑起来）真的被禁用了，在仓库内做一次提交（例如手动更新 `.github/keepalive.txt`）后，到 Actions 页面点 `Enable workflow` 即可恢复。

5. **心跳文件被误删**：`.github/keepalive.txt` 缺失不影响同步，下一次心跳会自动重建。

## 八、停用与排查

**临时停用**：Actions 页面 → 选中该 workflow → 右上角 `⋯` → `Disable workflow`。

**常见报错**：

| 报错 | 原因与处理 |
| --- | --- |
| `缺少 GITEE_USER 或 GITEE_TOKEN` | Secrets 未配置或名称拼写不符，按第三节重新配置 |
| `Authentication failed` / `403` | Gitee 令牌权限不足或已失效，重新生成并更新 `GITEE_TOKEN` |
| `无法读取 Gitee 的 main 分支` | Gitee 仓库尚未创建或名称不一致，检查仓库名是否与 GitHub 一致 |
| `合并产生冲突` | 两端并行提交且改到了同一处，查看该次运行的日志确认被覆盖的一侧，必要时手工恢复 |
| `两端 main 不一致，请先运行 scripts/sync.sh 对齐` | 心跳步骤的安全检查拦截。正常 workflow 流程中不会触发，只有在本机单独运行 `keepalive.sh` 时可能遇到 |
| `工作区存在未提交改动，为避免覆盖已中止` | 本机单独运行 `keepalive.sh` 时工作区不干净。先 commit 或 `git stash` 再运行 |
